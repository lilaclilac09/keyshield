The Race to 500 Milliseconds

A tiny Rust program that asks Solana a big question — and answers it before you can blink.

What is this thing?

sol-pnl-challenge is a CLI tool that does one job very fast: given a Solana wallet address, it returns how much SOL that wallet has gained or lost across its entire transaction history.

It was written for Mert's Solana dev weekend competition — a contest where the scoring metric was a single number: how many milliseconds your program took to return an answer.

⏱️
Why speed matters here

When a trading app shows you your PnL, every millisecond a user waits feels like an eternity. The techniques in this codebase — parallel requests, streaming results, smart chunking — are the exact same moves a senior backend engineer would pull to make a production dashboard feel instant.

What running it looks like

You hand the program a wallet and an RPC URL. It prints back JSON.

CODE 
$ sol-pnl-challenge \
    --address 7xKX...wallet \
    --rpc-url https://mainnet.helius-rpc.com/?api-key=XXX

{
  "address": "7xKX...wallet",
  "latencyMs": 487.3,
  "transactionCount": 3241,
  "pnlLamports": 412500000,
  "pnlSol": 0.4125
}
PLAIN ENGLISH

Run the tool with two required inputs: the wallet to analyze and where to ask for data.

It hits Helius — a beefy, paid Solana RPC provider — instead of the free public one (which is rate-limited to a crawl).

The result is a tidy JSON object: which wallet we checked, how long it took in milliseconds, how many transactions we processed, and the running profit or loss in both tiny units (lamports) and whole SOL.

Notice the latencyMs: 487.3 — that's the whole point of the exercise.

The shape of one run

Every run of the program does the same three things, in this order:

1
Parse the command-line arguments

Pull the wallet address and RPC URL out of what the user typed.

2
Race out to Helius and collect transactions

This is the expensive part — hundreds of parallel network calls, all of Module 3.

3
Add up the balance changes and print JSON

Each transaction tells us the wallet's balance before and after. Sum the differences → total PnL.

The target on the scoreboard

The README reports these cold-start times across wallets of different sizes:

💤

Sparse wallets

Under 500ms — a wallet with only a handful of transactions barely needs any network calls at all.

📊

Mid-activity

Around 400–500ms — a few hundred transactions, fits in the first couple of pages of Helius data.

🔥

High-activity

Under 600ms — even wallets with 3,000+ transactions finish before a slow blink.

These numbers are the entire reason this codebase exists. Every design choice you'll see — why the algorithm has three phases, why the HTTP client looks overbuilt, why there's a warm() function — traces back to shaving milliseconds off those totals.

Meet the Cast

Four Rust files, four very different jobs. If you know who does what, you know where to poke when something breaks.

An orchestra with four musicians

Think of the codebase as a small jazz quartet: a tiny group where every instrument is essential and nobody doubles up. One musician counts the tempo, one improvises the melody, one handles the phone calls to the venue, and one writes down the setlist. Remove any of them and the set falls apart.

🎯
main.rs — The Conductor

Reads command-line arguments, starts the stopwatch, calls the algorithm, adds up the numbers, prints the final JSON. About 70 lines. Knows almost nothing about how the work gets done.

🧭
algorithm.rs — The Strategist

The brain. Decides how to fetch transactions cheaply: which ranges to scout, which to fetch in full, which results to stream back first. This is where the 500ms magic lives.

📡
rpc.rs — The Courier

The one who actually talks to Helius. Builds JSON-RPC envelopes, compresses traffic, retries on failure. Doesn't care why anyone is asking.

📒
types.rs — The Ledger Keeper

Holds the BalancePoint — one tiny struct describing a single "the wallet had X lamports before this tx, Y after" observation. That's it. Twelve lines.

The entire vocabulary of the project, in one struct

Every number this program eventually prints comes from a list of BalancePoints. This is the only data shape you have to learn to understand the whole codebase.

types.rs 
/// One balance observation for a wallet at a specific transaction.
pub struct BalancePoint {
    pub slot: u64,
    pub block_time: Option<i64>,
    pub pre_lamports: u64,
    pub post_lamports: u64,
    pub signature: String,
}

impl BalancePoint {
    pub fn delta_lamports(&self) -> i128 {
        self.post_lamports as i128 - self.pre_lamports as i128
    }
}
PLAIN ENGLISH

A BalancePoint is a snapshot: "at transaction X, the wallet went from pre lamports to post lamports."

slot is Solana's version of a block number — a monotonically increasing ID for where this transaction landed in the chain's timeline.

block_time is the clock time the block was produced. Optional because very old blocks sometimes don't have it.

signature is the globally unique ID of the transaction — like a receipt number.

delta_lamports() is the money math: post minus pre. We use a bigger signed integer (i128) because the difference can be negative (you spent SOL) and can get very large when summed across thousands of transactions.

💡
Why integers, not floats

Money code in production almost never uses f64. Floats lose precision — add a billion transactions of 0.1 SOL and you won't land on exactly 100,000,000 SOL. Integers in lamports stay exact, and the conversion to f64 happens only once at the very end for display.

The Scout Strategy

The actual trick behind 500ms: don't fetch everything, fetch smart. Send scouts first, then send the heavy fetchers where the scouts report activity.

A wildfire-response metaphor

Imagine you're a fire-response coordinator and a wildfire has broken out somewhere in a long forested valley. You don't know exactly where it is. You have two kinds of units: spotter drones that are cheap and fly fast but can't put anything out, and tanker planes that can drop water but are slow and expensive per run.

The dumb play is to send tankers up and down the whole valley. The smart play is to launch spotter drones first — wide and parallel — and the moment a drone reports smoke, you dispatch a tanker to that exact coordinate, without waiting for the other drones to finish.

🔥
This is literally the algorithm

Helius gives you two kinds of API calls: signatures-mode (cheap, returns 1000 IDs per call — the drones) and full-mode (expensive, returns 100 fat transactions per call — the tankers). Both cost the same credit. Scouting with signatures first is how this algorithm learns the whole shape of a wallet cheaply, then only fires the heavy fetches where it knows transactions live.

Phase 0 in code: the one-round-trip opener

The very first thing the algorithm does is the highest-leverage move in the whole codebase.

algorithm.rs 
// ─── Phase 0: jackpot + tail in one RTT ───
let (jackpot, tail_resp) = tokio::try_join!(
    client.fetch_signatures(address, "asc",  SIG_LIMIT, None, None),
    client.fetch_signatures(address, "desc", SIG_LIMIT, None, None),
)?;
PLAIN ENGLISH

tokio::try_join! kicks off both requests at the same moment and waits for both to finish before moving on. If either errors, the whole thing aborts.

The first call asks for signatures in "asc" (ascending) order — the oldest 1000 transactions the wallet ever made. The code calls this the jackpot.

The second call asks for "desc" (descending) — the newest 1000 transactions (the tail).

Crucially, both go over the same HTTP/2 connection at once. One round-trip, two answers, and we've pinned both ends of the wallet's timeline. If the wallet has ≤2000 txs, we're basically done.

A subtle rule: slots are atomic

When the algorithm chunks signatures into ranges for bulk fetching, it has to respect a rule that's easy to miss. All transactions in the same slot have to stay together in the same chunk.

algorithm.rs — chunk_by_slot 
/// Group sigs into contiguous slot ranges of roughly `target` sigs
/// each. Never splits a single slot across chunks (a slot with N txs
/// must be fetched atomically — pagination tokens inside a slot are
/// opaque).
fn chunk_by_slot(sigs: &[SigResult], target: usize) -> Vec<(u64, u64)> {
    ...
    if count >= target {
        let next_slot = sigs.get(i + 1).map(|s| s.slot);
        match next_slot {
            Some(ns) if ns == sig.slot => continue,
            Some(ns) => { chunks.push((chunk_start, sig.slot + 1)); ... }
            ...
        }
    }
PLAIN ENGLISH

A slot is Solana's basic time unit, and multiple transactions can land in the same slot.

If we tried to fetch "the first 50 transactions in slots 100–200," but slot 150 alone had 80 transactions in it, Helius would paginate — and the pagination token it gives back is only valid within that exact request. We can't reuse it in a different parallel chunk.

So: if the chunk would end in the middle of a slot, keep adding sigs from that slot until the next slot appears, then cut. That's what the Some(ns) if ns == sig.slot => continue line does.

⚠️
The kind of bug that's hard to catch

If you split a slot across chunks, you don't get a loud error — you get silently missing transactions in your final PnL, only for whales who happen to do dozens of trades in a single 400ms slot. This is the kind of edge case that makes senior engineers suspicious of clever pagination.

Why dedup by signature?

At the end, the algorithm calls:

algorithm.rs — dedup 
all.sort_by(|a, b| a.slot.cmp(&b.slot)
    .then_with(|| a.signature.cmp(&b.signature)));
all.dedup_by(|a, b| a.signature == b.signature);
PLAIN ENGLISH

Because Phase 0 and Phase 1 can overlap in what they cover (the tail might bleed into a scouted region), the same transaction can end up fetched twice.

Deduping by signature — the transaction's globally unique ID — is the only correct way. Two different trades can happen in the same slot with the same pre/post balance (you swap tokens, SOL doesn't change), so slot-alone or balance-alone would falsely merge them.

The Speed Toolbox

A guided tour of the small-but-important tuning knobs that turn "fast enough" into "sub-500ms." Each one is a pattern you can ask AI to apply to your own network code.

Five dials, all turned up

Imagine tuning a race car. The engine (the algorithm) is doing its thing, but the tires, the aerodynamics, and the pit-stop choreography matter just as much. These are the five dials this codebase turns to shave milliseconds.

🛣️

HTTP/2 multiplexing

Open one TLS connection and run many parallel requests over it. No repeated handshake cost.

🗜️

Gzip + Brotli

JSON-RPC responses compress 5–10x. Ask the server to send compressed bytes.

🚦

Concurrency cap

A 100-slot semaphore stops the program from flooding Helius and getting rate-limited.

🔁

Exponential backoff

Retry on 429 / 5xx, doubling the wait each time. Five tries max. Typical production pattern.

🔥

Connection warm-up

Fire a tiny throwaway call before the real work so the TLS handshake isn't on the hot path.

The HTTP client, configured once

Every one of those five dials lives in a single block of code. Read the builder like a checklist of decisions.

rpc.rs — HeliusClient::new 
let client = Client::builder()
    .http2_adaptive_window(true)
    .http2_initial_stream_window_size(2 * 1024 * 1024)
    .http2_initial_connection_window_size(16 * 1024 * 1024)
    .tcp_nodelay(true)
    .pool_max_idle_per_host(100)
    .pool_idle_timeout(Duration::from_secs(90))
    .timeout(Duration::from_secs(30))
    .gzip(true)
    .brotli(true)
    .build()
    .expect("failed to build HTTP client");
PLAIN ENGLISH

The big window sizes (2MB per stream, 16MB per connection) tell HTTP/2 "don't choke me with flow control." Defaults assume tiny responses; ours are fat transaction pages.

tcp_nodelay disables Nagle's algorithm so small requests don't sit in a buffer waiting for more bytes to batch.

Keep up to 100 idle connections alive for 90 seconds so subsequent requests skip the TLS handshake entirely.

gzip and brotli ask Helius to compress its replies. A 2MB JSON response can arrive as 200KB of bytes.

The warm-up: priming the engine

Before the real work starts, main.rs does something that looks pointless.

main.rs 
let (_, balances) = tokio::try_join!(
    client.warm(),
    algorithm::compute(&client, &args.address),
)?;
PLAIN ENGLISH

It runs warm() — a tiny dummy call — in parallel with the real computation.

warm() opens the TCP+TLS+HTTP/2 connection and pings the server with a trivial request. That "boring" work would otherwise happen on the first real request and tack extra milliseconds onto the critical path.

By running both together with try_join!, the handshake completes in the background while the algorithm is doing its own setup. The real fetches land on an already-hot connection.

Retries done right

Networks fail. Servers get overloaded. A production-grade client retries — but smartly.

rpc.rs — the retry loop 
for attempt in 0..5u32 {
    let http = self.client.post(&self.rpc_url)
        .json(&request).send().await?;
    let status = http.status();
    if status == 429 || status.is_server_error() {
        if attempt < 4 {
            let ms = 100 * 2u64.pow(attempt);
            tokio::time::sleep(Duration::from_millis(ms)).await;
            continue;
        }
        bail!("HTTP {status} after {attempt} retries");
    }
    ...
}
PLAIN ENGLISH

Try up to 5 times total. On each retry, sleep longer than the last: 100ms, then 200, 400, 800. This is exponential backoff.

Only retry on the errors that are worth retrying: 429 (rate-limited) and 5xx (server having a bad day). Don't retry on 4xx — those mean you did something wrong and retrying won't fix it.

The loop also specifically retries on Solana's custom RPC error code -32429, which is how Helius signals rate-limiting inside the JSON-RPC envelope (not at the HTTP layer).

💡
Universal pattern

Exponential backoff with a cap on attempts is the standard retry recipe for any production client talking to any flaky dependency — databases, payment processors, other internal services. If you're ever asking an AI to write network code, say "use exponential backoff with 5 max attempts, only retry on 429 and 5xx."
