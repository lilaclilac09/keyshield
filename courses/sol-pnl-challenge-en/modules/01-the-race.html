The Race to 500 Milliseconds

A tiny Rust program that asks Solana a big question — and answers it before you can blink.

What is this thing?

sol-pnl-challenge is a CLI tool that does one job very fast: given a Solana wallet address, it returns how much SOL that wallet has gained or lost across its entire transaction history.

It was written for Mert's Solana dev weekend competition — a contest where the scoring metric was a single number: how many milliseconds your program took to return an answer.

⏱️
Why speed matters here

When a trading app shows you your PnL, every millisecond a user waits feels like an eternity. The techniques in this codebase — parallel requests, streaming results, smart chunking — are the exact same moves a senior backend engineer would pull to make a production dashboard feel instant.

What running it looks like

You hand the program a wallet and an RPC URL. It prints back JSON.

CODE 
$ sol-pnl-challenge \
    --address 7xKX...wallet \
    --rpc-url https://mainnet.helius-rpc.com/?api-key=XXX

{
  "address": "7xKX...wallet",
  "latencyMs": 487.3,
  "transactionCount": 3241,
  "pnlLamports": 412500000,
  "pnlSol": 0.4125
}
PLAIN ENGLISH

Run the tool with two required inputs: the wallet to analyze and where to ask for data.

It hits Helius — a beefy, paid Solana RPC provider — instead of the free public one (which is rate-limited to a crawl).

The result is a tidy JSON object: which wallet we checked, how long it took in milliseconds, how many transactions we processed, and the running profit or loss in both tiny units (lamports) and whole SOL.

Notice the latencyMs: 487.3 — that's the whole point of the exercise.

The shape of one run

Every run of the program does the same three things, in this order:

1
Parse the command-line arguments

Pull the wallet address and RPC URL out of what the user typed.

2
Race out to Helius and collect transactions

This is the expensive part — hundreds of parallel network calls, all of Module 3.

3
Add up the balance changes and print JSON

Each transaction tells us the wallet's balance before and after. Sum the differences → total PnL.

The target on the scoreboard

The README reports these cold-start times across wallets of different sizes:

💤

Sparse wallets

Under 500ms — a wallet with only a handful of transactions barely needs any network calls at all.

📊

Mid-activity

Around 400–500ms — a few hundred transactions, fits in the first couple of pages of Helius data.

🔥

High-activity

Under 600ms — even wallets with 3,000+ transactions finish before a slow blink.

These numbers are the entire reason this codebase exists. Every design choice you'll see — why the algorithm has three phases, why the HTTP client looks overbuilt, why there's a warm() function — traces back to shaving milliseconds off those totals.
