The Scout Strategy

The actual trick behind 500ms: don't fetch everything, fetch smart. Send scouts first, then send the heavy fetchers where the scouts report activity.

A wildfire-response metaphor

Imagine you're a fire-response coordinator and a wildfire has broken out somewhere in a long forested valley. You don't know exactly where it is. You have two kinds of units: spotter drones that are cheap and fly fast but can't put anything out, and tanker planes that can drop water but are slow and expensive per run.

The dumb play is to send tankers up and down the whole valley. The smart play is to launch spotter drones first — wide and parallel — and the moment a drone reports smoke, you dispatch a tanker to that exact coordinate, without waiting for the other drones to finish.

🔥
This is literally the algorithm

Helius gives you two kinds of API calls: signatures-mode (cheap, returns 1000 IDs per call — the drones) and full-mode (expensive, returns 100 fat transactions per call — the tankers). Both cost the same credit. Scouting with signatures first is how this algorithm learns the whole shape of a wallet cheaply, then only fires the heavy fetches where it knows transactions live.

Phase 0 in code: the one-round-trip opener

The very first thing the algorithm does is the highest-leverage move in the whole codebase.

algorithm.rs 
// ─── Phase 0: jackpot + tail in one RTT ───
let (jackpot, tail_resp) = tokio::try_join!(
    client.fetch_signatures(address, "asc",  SIG_LIMIT, None, None),
    client.fetch_signatures(address, "desc", SIG_LIMIT, None, None),
)?;
PLAIN ENGLISH

tokio::try_join! kicks off both requests at the same moment and waits for both to finish before moving on. If either errors, the whole thing aborts.

The first call asks for signatures in "asc" (ascending) order — the oldest 1000 transactions the wallet ever made. The code calls this the jackpot.

The second call asks for "desc" (descending) — the newest 1000 transactions (the tail).

Crucially, both go over the same HTTP/2 connection at once. One round-trip, two answers, and we've pinned both ends of the wallet's timeline. If the wallet has ≤2000 txs, we're basically done.

A subtle rule: slots are atomic

When the algorithm chunks signatures into ranges for bulk fetching, it has to respect a rule that's easy to miss. All transactions in the same slot have to stay together in the same chunk.

PLAIN ENGLISH

A slot is Solana's basic time unit, and multiple transactions can land in the same slot.

If we tried to fetch "the first 50 transactions in slots 100–200," but slot 150 alone had 80 transactions in it, Helius would paginate — and the pagination token it gives back is only valid within that exact request. We can't reuse it in a different parallel chunk.

So: if the chunk would end in the middle of a slot, keep adding sigs from that slot until the next slot appears, then cut. That's what the Some(ns) if ns == sig.slot => continue line does.

⚠️
The kind of bug that's hard to catch

If you split a slot across chunks, you don't get a loud error — you get silently missing transactions in your final PnL, only for whales who happen to do dozens of trades in a single 400ms slot. This is the kind of edge case that makes senior engineers suspicious of clever pagination.

Why dedup by signature?

At the end, the algorithm calls:

algorithm.rs — dedup 
all.sort_by(|a, b| a.slot.cmp(&b.slot)
    .then_with(|| a.signature.cmp(&b.signature)));
all.dedup_by(|a, b| a.signature == b.signature);
PLAIN ENGLISH

Because Phase 0 and Phase 1 can overlap in what they cover (the tail might bleed into a scouted region), the same transaction can end up fetched twice.

Deduping by signature — the transaction's globally unique ID — is the only correct way. Two different trades can happen in the same slot with the same pre/post balance (you swap tokens, SOL doesn't change), so slot-alone or balance-alone would falsely merge them.
