01

500 毫秒之战

一个小巧的 Rust 程序，向 Solana 问一个大问题 —— 并在你眨眼之前给出答案。

这个工具到底是干什么的？

sol-pnl-challenge 是一个CLI 工具，它只做一件事，而且做得极快：给它一个 Solana 钱包地址，它会告诉你这个钱包在整条历史记录里一共赚了（或亏了）多少 SOL。

它的诞生场合是 Mert 的 Solana 开发周末挑战赛 —— 一场评分标准只有一个数字的比赛：你的程序返回答案要花多少毫秒。

⏱️
为什么速度在这里如此重要

当交易类应用向用户展示PnL 时，用户每多等一毫秒都像过了一个世纪。这份代码里用到的技巧 —— 并行请求、流式处理、智能分片 —— 正是资深后端工程师让生产仪表盘"一瞬即现"的那套招数。

运行起来长什么样

你给它一个钱包地址和一个 RPC URL，它就会吐出一段 JSON。

CODE 
$ sol-pnl-challenge \
    --address 7xKX...wallet \
    --rpc-url https://mainnet.helius-rpc.com/?api-key=XXX

{
  "address": "7xKX...wallet",
  "latencyMs": 487.3,
  "transactionCount": 3241,
  "pnlLamports": 412500000,
  "pnlSol": 0.4125
}
大白话

带两个必填参数运行工具：要分析的钱包，以及去哪里取数据。

它去访问 Helius —— 一家性能强劲的付费 Solana RPC 服务商 —— 而不是公共免费端点（后者被限流限得龟速）。

结果是一个整洁的 JSON：我们查了哪个钱包，花了多少毫秒，处理了多少笔交易，以及用两种单位（lamports 和整 SOL）表示的盈亏。

注意 latencyMs: 487.3 —— 整个挑战的核心，就在这一个数字上。

一次运行的三段式

这个程序每次运行都是同样的三步，按顺序进行：

1
解析命令行参数

从用户输入的内容里把钱包地址和 RPC URL 取出来。

2
飞奔到 Helius 收集交易

这是最贵的一段 —— 几百个并行网络请求，也是整个模块 3 的重头戏。

3
把余额变化累加起来，打印 JSON

每笔交易都告诉我们钱包"交易前"和"交易后"的余额。把差值加起来 → 总盈亏。

赛道上的目标时间

README 报告了在不同活跃度的钱包上冷启动时间：

💤

低活跃钱包

500 毫秒以内 —— 只有寥寥几笔交易的钱包几乎不需要发多少网络请求。

📊

中等活跃

大约 400–500 毫秒 —— 几百笔交易，Helius 头几页数据就能装下。

🔥

高活跃钱包

600 毫秒以内 —— 连 3000 多笔交易的钱包也能在一次慢眨眼前完成。

这些数字是整份代码存在的唯一理由。你接下来会看到的所有设计决策 —— 为什么算法分三阶段、为什么 HTTP 客户端看上去"过度配置"、为什么还要有个 warm() 函数 —— 全都是为了从这些总时间里再抠出几毫秒。

types.rs — 账本管理员

只持有 BalancePoint —— 一个描述单笔交易"前余额 X lamports，后余额 Y"的微型结构体。就这样。十二行。

整个项目的词汇量，浓缩在一个结构体里

这个程序最终打印出的每一个数字，都来自一串 BalancePoint。这是你理解整份代码唯一需要掌握的数据形态。

types.rs 
/// One balance observation for a wallet at a specific transaction.
pub struct BalancePoint {
    pub slot: u64,
    pub block_time: Option<i64>,
    pub pre_lamports: u64,
    pub post_lamports: u64,
    pub signature: String,
}

impl BalancePoint {
    pub fn delta_lamports(&self) -> i128 {
        self.post_lamports as i128 - self.pre_lamports as i128
    }
}
大白话

一个 BalancePoint 就是一张快照："在第 X 笔交易处，钱包余额从 pre lamports 变成了 post lamports。"

slot 是 Solana 版的"区块号" —— 单调递增的 ID，标记这笔交易落在链上时间线的哪一格。

block_time 是出块的时间戳。可选，因为一些非常老的区块没有这个字段。

signature 是该笔交易的全局唯一 ID —— 相当于收据号。

delta_lamports() 是金额运算：post 减 pre。用更大的有符号整数（i128）是因为差值可能为负（你花掉了 SOL），也可能在几千笔交易累加后变得非常大。

💡
为什么用整数而不是浮点

生产级的金额代码几乎从不用 f64。浮点数会丢精度 —— 把十亿笔 0.1 SOL 累加起来，你得不到正好 100,000,000 SOL。用 lamports 的整数保持精确，只在最后一步为了展示才转成 f64。

侦察兵策略

500 毫秒背后真正的门道：不是全量抓取，而是聪明地抓。先派侦察兵跑一圈，等他们汇报哪里有动静，再派重型部队精准出击。

一场森林灭火的比喻

想象你是森林火灾应急指挥官。山谷里某处起了火，你不知道具体位置。你手上有两种兵力：侦察无人机又轻又快成本又低，但它没法灭火；消防飞机能洒水，但每架都慢又贵。

最笨的办法是让消防飞机从山谷一头排查到另一头。聪明的办法是先放无人机 —— 大面积并行出动；一旦某架无人机发现冒烟，立刻派消防飞机去那个坐标，不必等其他无人机全部回来。

🔥
这就是算法的原样

Helius 提供两种调用：签名模式（便宜，每次返回 1000 个 ID —— 无人机）和完整模式（贵，每次返回 100 笔厚重交易 —— 消防飞机）。两者消耗的credits相同，但签名一次能多拿 10 倍的行数。所以先用签名侦察就能以极低成本摸清钱包全貌，再把昂贵的完整拉取只打向真正有交易的区段。

阶段 0 的代码：一次往返的开局

算法做的第一件事，就是全份代码里杠杆最大的一招。

algorithm.rs 
// ─── Phase 0: jackpot + tail in one RTT ───
let (jackpot, tail_resp) = tokio::try_join!(
    client.fetch_signatures(address, "asc",  SIG_LIMIT, None, None),
    client.fetch_signatures(address, "desc", SIG_LIMIT, None, None),
)?;
大白话

tokio::try_join! 把两个请求在同一时刻启动，等两边都完成才往下走。任何一个报错，整体立即中止。

第一个请求按 "asc"（升序）方向取签名 —— 钱包最早的 1000 笔交易。代码里给它起的名字叫头奖（jackpot）。

第二个请求用 "desc"（降序）—— 钱包最新的 1000 笔交易（尾部）。

关键是，两者走同一条 HTTP/2 连接同时发。一次往返，两份回答，我们就把钱包时间线的两端钉住了。如果钱包总交易数 ≤ 2000 笔，基本已经完事。

一条容易被忽略的规则：slot 是原子的

算法把签名切片分块时，需要遵守一条一不留神就踩坑的规则：同一个 slot 里的所有交易必须待在同一个块里。

大白话

slot是 Solana 的基本时间单位，同一个 slot 里可能有多笔交易。

如果我们让 Helius"给我 slot 100–200 范围里最早的 50 笔交易"，而 slot 150 一个 slot 里就有 80 笔，它会分页返回 —— 它给的分页令牌只对那次请求本身有效，换到另一个并行块里就没法复用。

所以：如果当前块正好切在一个 slot 中间，就继续把这个 slot 剩下的签名都收进来，等遇到新的 slot 再切。Some(ns) if ns == sig.slot => continue 这一行做的正是这件事。

⚠️
最难察觉的那类 bug

如果你在 slot 中间硬切，你不会收到醒目的报错 —— 只会在最终 PnL 里悄悄少一些交易，而且只在那种一个 400 毫秒的 slot 里就做了十几笔交易的大户钱包上出现。这类边角案例，正是资深工程师对"花式分页"保持警惕的原因。

为什么按签名去重？

最后一步算法做的是：

algorithm.rs — dedup 
all.sort_by(|a, b| a.slot.cmp(&b.slot)
    .then_with(|| a.signature.cmp(&b.signature)));
all.dedup_by(|a, b| a.signature == b.signature);
大白话

因为阶段 0 和阶段 1 覆盖的区段可能重叠（尾部会"渗"进侦察区段），同一笔交易可能被拉两次。

按 signature（交易的全局唯一 ID）去重，是唯一正确的做法。两笔不同的交易可能在同一个 slot 内发生、pre/post 余额也相同（比如你换了代币、SOL 没变），只按 slot 或只按余额去重会把它们错误地合并成一笔。

加速工具箱

一圈不起眼却关键的调优开关，把"够快"变成"500 毫秒以内"。每一个都是你可以让 AI 套到自己网络代码上的模式。

五个旋钮，全部拧到底

把这个场景想象成给一辆赛车调校。引擎（算法）在做它的事，但轮胎、空气动力、维修站的换胎编排同样至关重要。这份代码里拧的正是这五个旋钮。

🛣️

HTTP/2 多路复用

只开一条 TLS 连接，在上面跑许多并行请求。省掉反复握手的代价。

🗜️

Gzip + Brotli

JSON-RPC 响应能压到 5–10 分之一。直接让服务端发压缩字节。

🚦

并发上限

一个容量 100 的信号量，避免把 Helius 冲垮招来限流。

🔁

指数退避

遇到 429 / 5xx 就重试，每次等待时间翻倍。最多 5 次。典型的生产级模式。

🔥

连接预热

在真正开工之前先发一个无关痛痒的小请求，把 TLS 握手的代价从主路径上挪开。

HTTP 客户端一次性配置好

上面五个旋钮，都活在同一段代码里。把这段 builder 当成一张决策清单来读。

rpc.rs — HeliusClient::new 
let client = Client::builder()
    .http2_adaptive_window(true)
    .http2_initial_stream_window_size(2 * 1024 * 1024)
    .http2_initial_connection_window_size(16 * 1024 * 1024)
    .tcp_nodelay(true)
    .pool_max_idle_per_host(100)
    .pool_idle_timeout(Duration::from_secs(90))
    .timeout(Duration::from_secs(30))
    .gzip(true)
    .brotli(true)
    .build()
    .expect("failed to build HTTP client");
大白话

那两个大窗口值（每流 2MB、每连接 16MB）是在告诉 HTTP/2："别用流控卡我。"默认值是为小响应优化的；我们这里是胖胖的交易数据页。

tcp_nodelay 关闭 Nagle 算法，让小请求不至于在缓冲区里干等着凑一批。

保留最多 100 条空闲连接，空闲 90 秒内不回收，这样后续请求就能跳过 TLS 握手。

gzip 和 brotli 告诉 Helius 压缩回包。2MB 的 JSON 响应能以 200KB 的体量到达。

预热：给引擎打火

在真正开工之前，main.rs 做了一件看起来毫无意义的事。

main.rs 
let (_, balances) = tokio::try_join!(
    client.warm(),
    algorithm::compute(&client, &args.address),
)?;
大白话

它让 warm()（一个微型空调用）和真正的计算并行运行。

warm() 会打开 TCP + TLS + HTTP/2 连接，并向服务端 ping 一个无关紧要的请求。这些"没劲"的工作，否则会堆在第一次真实请求之前，把几毫秒硬加到关键路径上。

用 try_join! 两者同时跑，握手在后台进行的时候，算法已经在做它自己的准备工作。真正的拉取落在一条已经热起来的连接上。

优雅的重试

网络会抖，服务器会过载。生产级客户端会重试 —— 但必须聪明地重试。

rpc.rs — the retry loop 
for attempt in 0..5u32 {
    let http = self.client.post(&self.rpc_url)
        .json(&request).send().await?;
    let status = http.status();
    if status == 429 || status.is_server_error() {
        if attempt < 4 {
            let ms = 100 * 2u64.pow(attempt);
            tokio::time::sleep(Duration::from_millis(ms)).await;
            continue;
        }
        bail!("HTTP {status} after {attempt} retries");
    }
    ...
}
大白话

最多重试 5 次。每次比上次睡得久：100、200、400、800 毫秒。这就是指数退避。

只对值得重试的错误重试：429（限流）和 5xx（服务端抽风）。不要对 4xx 重试 —— 那是你自己做错了，再试多少次也不会对。

循环里还专门对 Solana 自定义的 RPC 错误码 -32429 重试，这是 Helius 在 JSON-RPC 包体里（不是在 HTTP 层）表示限流的方式。

💡
通用模式

带次数上限的指数退避，是任何生产客户端对任何不稳定依赖（数据库、支付网关、其他内部服务）的标准重试配方。你要是让 AI 写网络代码，就说"用 5 次上限的指数退避，只在 429 和 5xx 时重试"。
