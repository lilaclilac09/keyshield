侦察兵策略

500 毫秒背后真正的门道：不是全量抓取，而是聪明地抓。先派侦察兵跑一圈，等他们汇报哪里有动静，再派重型部队精准出击。

一场森林灭火的比喻

想象你是森林火灾应急指挥官。山谷里某处起了火，你不知道具体位置。你手上有两种兵力：侦察无人机又轻又快成本又低，但它没法灭火；消防飞机能洒水，但每架都慢又贵。

最笨的办法是让消防飞机从山谷一头排查到另一头。聪明的办法是先放无人机 —— 大面积并行出动；一旦某架无人机发现冒烟，立刻派消防飞机去那个坐标，不必等其他无人机全部回来。

🔥
这就是算法的原样

Helius 提供两种调用：签名模式（便宜，每次返回 1000 个 ID —— 无人机）和完整模式（贵，每次返回 100 笔厚重交易 —— 消防飞机）。两者消耗的credits相同，但签名一次能多拿 10 倍的行数。所以先用签名侦察就能以极低成本摸清钱包全貌，再把昂贵的完整拉取只打向真正有交易的区段。

阶段 0 的代码：一次往返的开局

算法做的第一件事，就是全份代码里杠杆最大的一招。

algorithm.rs 
// ─── Phase 0: jackpot + tail in one RTT ───
let (jackpot, tail_resp) = tokio::try_join!(
    client.fetch_signatures(address, "asc",  SIG_LIMIT, None, None),
    client.fetch_signatures(address, "desc", SIG_LIMIT, None, None),
)?;
大白话

tokio::try_join! 把两个请求在同一时刻启动，等两边都完成才往下走。任何一个报错，整体立即中止。

第一个请求按 "asc"（升序）方向取签名 —— 钱包最早的 1000 笔交易。代码里给它起的名字叫头奖（jackpot）。

第二个请求用 "desc"（降序）—— 钱包最新的 1000 笔交易（尾部）。

关键是，两者走同一条 HTTP/2 连接同时发。一次往返，两份回答，我们就把钱包时间线的两端钉住了。如果钱包总交易数 ≤ 2000 笔，基本已经完事。

一条容易被忽略的规则：slot 是原子的

算法把签名切片分块时，需要遵守一条一不留神就踩坑的规则：同一个 slot 里的所有交易必须待在同一个块里。

大白话

slot是 Solana 的基本时间单位，同一个 slot 里可能有多笔交易。

如果我们让 Helius"给我 slot 100–200 范围里最早的 50 笔交易"，而 slot 150 一个 slot 里就有 80 笔，它会分页返回 —— 它给的分页令牌只对那次请求本身有效，换到另一个并行块里就没法复用。

所以：如果当前块正好切在一个 slot 中间，就继续把这个 slot 剩下的签名都收进来，等遇到新的 slot 再切。Some(ns) if ns == sig.slot => continue 这一行做的正是这件事。

⚠️
最难察觉的那类 bug

如果你在 slot 中间硬切，你不会收到醒目的报错 —— 只会在最终 PnL 里悄悄少一些交易，而且只在那种一个 400 毫秒的 slot 里就做了十几笔交易的大户钱包上出现。这类边角案例，正是资深工程师对"花式分页"保持警惕的原因。

为什么按签名去重？

最后一步算法做的是：

algorithm.rs — dedup 
all.sort_by(|a, b| a.slot.cmp(&b.slot)
    .then_with(|| a.signature.cmp(&b.signature)));
all.dedup_by(|a, b| a.signature == b.signature);
大白话

因为阶段 0 和阶段 1 覆盖的区段可能重叠（尾部会"渗"进侦察区段），同一笔交易可能被拉两次。

按 signature（交易的全局唯一 ID）去重，是唯一正确的做法。两笔不同的交易可能在同一个 slot 内发生、pre/post 余额也相同（比如你换了代币、SOL 没变），只按 slot 或只按余额去重会把它们错误地合并成一笔。
