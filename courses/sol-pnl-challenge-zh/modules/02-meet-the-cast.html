认识四位主角

四个 Rust 文件，四种截然不同的职责。知道谁管什么，就知道出问题时该戳哪里。

一个四人爵士乐队

把这份代码想象成一个小型爵士四重奏：人数不多，每件乐器都不可或缺，也没有谁跟谁重复。一个人打拍子，一个人即兴旋律，一个人负责跟演出场地通电话，一个人记录曲目单。少任何一个，演出都撑不起来。

🎯
main.rs — 指挥家

读取命令行参数、启动秒表、调用算法、汇总数字、打印最终 JSON。约 70 行。几乎不关心具体怎么干活。

🧭
algorithm.rs — 策略师

大脑所在。决定怎么低成本地获取交易：哪些区间去侦察、哪些要完整拉取、哪些结果先流回来。500 毫秒的魔法就住在这里。

📡
rpc.rs — 信使

真正跟 Helius 通信的那一位。构造 JSON-RPC 请求、压缩流量、失败重试。不关心为什么要发这些请求。

📒
types.rs — 账本管理员

只持有 BalancePoint —— 一个描述单笔交易"前余额 X lamports，后余额 Y"的微型结构体。就这样。十二行。

整个项目的词汇量，浓缩在一个结构体里

这个程序最终打印出的每一个数字，都来自一串 BalancePoint。这是你理解整份代码唯一需要掌握的数据形态。

types.rs 
/// One balance observation for a wallet at a specific transaction.
pub struct BalancePoint {
    pub slot: u64,
    pub block_time: Option<i64>,
    pub pre_lamports: u64,
    pub post_lamports: u64,
    pub signature: String,
}

impl BalancePoint {
    pub fn delta_lamports(&self) -> i128 {
        self.post_lamports as i128 - self.pre_lamports as i128
    }
}
大白话

一个 BalancePoint 就是一张快照："在第 X 笔交易处，钱包余额从 pre lamports 变成了 post lamports。"

slot 是 Solana 版的"区块号" —— 单调递增的 ID，标记这笔交易落在链上时间线的哪一格。

block_time 是出块的时间戳。可选，因为一些非常老的区块没有这个字段。

signature 是该笔交易的全局唯一 ID —— 相当于收据号。

delta_lamports() 是金额运算：post 减 pre。用更大的有符号整数（i128）是因为差值可能为负（你花掉了 SOL），也可能在几千笔交易累加后变得非常大。

💡
为什么用整数而不是浮点

生产级的金额代码几乎从不用 f64。浮点数会丢精度 —— 把十亿笔 0.1 SOL 累加起来，你得不到正好 100,000,000 SOL。用 lamports 的整数保持精确，只在最后一步为了展示才转成 f64。
