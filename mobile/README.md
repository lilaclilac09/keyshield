# @keyshield/mobile — React Native skeleton

This workspace ships the JavaScript / TypeScript layer of a future
KeyShield iOS + Android app. It deliberately reuses everything in
`@keyshield/extension-sync` — same `auth.ts`, `vault.ts`, `sync.ts`,
`mnemonic.ts`, `seed-envelope.ts`, `conflict.ts`, `useVaultFlow`
hook — and only adds platform adapters for the things that differ
on a phone:

| Capability | Browser (extension-sync) | Mobile (this workspace) |
|---|---|---|
| Storage | `chrome.storage.local` | AsyncStorage via `asyncStorageBackend` |
| Web Crypto | `globalThis.crypto` (DOM) | `react-native-quick-crypto` via `cryptoBackend` |
| WebAuthn | `navigator.credentials` | `react-native-passkey` (adapter is TODO; see below) |

Everything else — the dual-write sync model, BIP-39 recovery,
tombstone merge, post-recovery passkey enrollment — is the same
code path on both platforms.

## What you need to actually run it on a phone

1. `npx react-native init keyshield-app --skip-install` outside
   the workspace tree (the generated `ios/` + `android/` folders
   should NOT live inside the npm workspace because Cocoapods +
   Gradle don't play nicely with hoisted node_modules).
2. In the generated app's `package.json`, add `@keyshield/mobile`
   as a `file:` dependency pointing at this directory.
3. `pod install` in `ios/`, `./gradlew :app:installDebug` for
   Android.
4. Implement the bodies of `passkeyAdapter.ts` using
   `Passkey.create()` / `Passkey.get()` from `react-native-passkey`
   3.x with `extensions: { prf: { eval: { first: PRF_SALT } } }`.
   Reshape the response into the Credential-like object
   `auth.ts`'s `credentialToRegistrationJSON` /
   `credentialToAuthenticationJSON` helpers expect.
5. Replace the placeholder screen Text blocks in `AppShell.tsx`
   with real RN ports of the corresponding extension screens.

## Why React Native, not native Swift / Kotlin

We picked RN because it lets us reuse 100% of the lib code:

- `auth.ts`, `vault.ts`, `sync.ts`, `sync-auth.ts`,
  `mnemonic.ts`, `seed-envelope.ts`, `conflict.ts`, `platform.ts`
  — all run on Hermes unchanged.
- `useVaultFlow`, the state machine that took five Phase commits
  to get right, ports across because it's pure React.
- The 304 cross-workspace tests we already maintain cover the
  shared logic; mobile-specific tests just need to cover the
  adapters.

A native Swift app would mean reimplementing all of the above in
CryptoKit + Foundation. That's the right move long-term but not
the right "first ship a mobile build" move.
