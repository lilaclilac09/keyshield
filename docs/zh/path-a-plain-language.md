# KeyShield Path A：密码学在说什么「人话」

这篇用生活比喻解释 Vault（路径 A）在做什么，**不讲公式推导**，只讲「你得到了什么、服务器永远拿不到什么」。

---

## 一句话

**你的 API 密钥在浏览器里被一把「只有你能造出来的钥匙」锁进保险箱；上传到我们这边的只有乱码（密文），没有第二个人能替你打开。**

---

## 五个概念，用人话说

### 1. WebAuthn / 人脸、指纹、Passkey 是在干什么？

不是「帮我们网站登录」这么简单。对你而言：这是 **「证明此刻操作的人是你持握的设备」** 的一种门。

KeyShield 利用同一套能力，从这次验证里导出一段 **只有你这台设备、这次会话能稳定重现的材料**，当作后续加密的根——**服务器不参与造这把根钥匙**。

### 2. PRF 是什么（不说数学版）

想象成：把上面那段材料 **喂进一个单向搅拌机**，出来的是一段固定长度的随机-looking 字节。你没法从搅拌机输出反推输入，但同一输入永远出同一输出。

**人话**：= **「从你身上取出的一段指纹盐」**，用来做下一步密钥推导，而不是把明文密钥存数据库。

### 3. HKDF

把「搅拌机出来的材料」再 **规整成标准长度的加密主密钥材料**（像把粗盐筛成配方要求的细盐）。

### 4. AES-256-GCM

业界常用的 **对称加密**：同一把密钥可以加密、解密。GCM 模式还带 **完整性校验**——密文被改过会在解密时失败，而不是悄悄给你假数据。

**人话**：明文进了 AES，出来的就是 **谁都看不懂的 ciphertext**；没有密钥的人在计算上无法还原。

### 5. 「Zero-knowledge / 零知识」在这里指什么？

不是学术里完整的 ZK 证明，而是产品设计上的含义：

- **我们的 API / 同步层只处理 ciphertext**（以及你的身份令牌能访问哪块密文）。
- **明文密钥不出浏览器（Path A 存储路径）**；我们不在磁盘上存一份「能直接用的 sk-」。

所以广告里说 **「架构上读不懂你的保险库」** 的意思是：**没有密钥材料，服务器看到的只是一包加密后的 blob。**

## 串起来：一次「存密钥」流水账

1. 你在网页里点保存密钥。
2. 浏览器完成钱包 / Passkey 验证，得到 **只有客户端掌握的根材料**。
3. 推导出一把 **AES 密钥**（只在内存里，用于这一步）。
4. 你的 `sk-…` 被 AES 加密 → **ciphertext**。
5. 上传的是 ciphertext + 必要的元数据；**没有 sk 明文随 HTTP 上传**（在该路径下）。

之后每一次「代理调上游」：有会话、有权限的客户端才能从自己的流程里拿到解密能力；代理侧用法是 **按请求解密再转发、不落盘**（见主 README 与 `docs/API.md`）。

---

## 你仍然要记得的事（诚实边界）

- **终端 / 脚本里的 `KS_TOKEN`** 能代表「你授权这个运行时去用代理」——要当密码一样保管、轮转。
- **设备丢了** 时，防护取决于你是否还有备份 / 另一台已信任设备、以及钱包与 Passkey 的恢复策略。
- 「零知识」描述的是 **服务器侧不持明文**，不是「永远没有任何风险」——**端点安全**仍然重要。
